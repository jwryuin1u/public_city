읽는 법: 수용 기준은 EARS 표기를 쓴다. `WHEN`(~하면), `IF`(~인 경우, 주로 오류), `WHILE`(~인 동안), `WHERE`(~기능이 있을 때), `SHALL`(반드시 ~한다)은 표기 규칙이라 영어로 둔다. "시스템"은 이 PoC에서 만드는 전체를 가리킨다.

## Problem Statement

S&OP 담당자 한 명이 매일 개인 PC에서 입력 10종을 손으로 모아 재고배분 프로그램(pipeline.py)을 돌리고 결과를 ERP에 직접 올린다. 입력이 빠져도 알 수 없고(2026-08-13에 6개 카테고리 중 4개만 추출됨), 프로그램을 고친 뒤 결과가 맞는지는 사람이 눈으로 확인하며, 설정과 결과가 개인 PC에만 남는다.

고객은 이 프로그램을 Azure로 옮겨 자동 연계 데이터로 실행·검증할 수 있는지 PoC로 확인한 뒤 본 구축에 착수한다.

## Goals

- [ ] 기준 입력과 운영 파라미터로 실행한 결과가 현행 PC에서 같은 날 실행한 결과와 셀 단위로 같다
- [ ] 현업이 고친 pipeline.py를 올려 실행하고, 운영 버전 결과와의 차이(건수 4종, 달라진 SKU)를 화면에서 본다
- [ ] 대상 카테고리가 빠진 입력은 실행되지 않는다
- [ ] 업무 규칙 5개를 자동으로 확인하고, 위반이 있으면 운영 결과 승인과 운영 반영 요청이 거절된다
- [ ] 접근이 승인된 기간계 원천은 사람 손을 거치지 않고 수집되어 일자별 입력 묶음이 된다
- [ ] 수집 시작부터 결과 승인까지 걸린 시간을 구간별로 기록해 현행(09:00~10:30)과 비교한다
- [ ] 검증 결과의 이상치를 작성자와 점별 바이어에게 묻고, 답변을 반영한 재테스트에서 이상치별 처리 상태를 본다

## Out of Scope

| Feature | Reason |
| --- | --- |
| ERP 자동 반영 | 고객이 협의 대상으로 분류. PoC는 결과 파일을 내려받아 현행대로 직접 올린다 |
| 배분 로직 변경, 코드 정리 | 현행과 같은 결과를 확인하는 것이 목적이다 |
| 컬럼 위치 오류 수정 (코너 자리에서 발주번호를 읽음) | 고치면 현행 결과와 비교할 수 없다. 수정 시점은 고객 확인 사항 |
| 재고배분 외 다른 프로그램 수용 | 고객 PPT 5쪽의 AI 샌드박스는 본사업 방향 |
| LLM 서비스 연계 | 의미가 정해지지 않았다. 이상치 질문 문안도 유형별 고정 문안을 쓴다 |
| MD 마스터의 화면 편집 | PoC는 엑셀 올리기와 버전 보관까지 |
| 입력 파일 인코딩 통일(UTF-8) | 현행 형식을 바꾸면 프로그램이 다르게 읽을 수 있다 |
| 새 라이브러리가 필요한 프로그램 수정 | 실행 환경 변경이 필요하다. 본사업에서 다룬다 |
| 사용자·권한 관리 화면, 스케줄 관리 화면 | Azure 설정으로 처리한다 |
| 점·채널 정의 등 코드에 고정된 규칙의 설정화 | 본사업 과제 |
| 클라우드 결과의 실제 ERP 반영 | PoC 기간에는 현행 PC 결과를 ERP에 올린다. 클라우드는 비교용으로 병행한다 |

## User Stories

### P1: 기간계 데이터 자동 수집 ⭐ MVP

**User Story**: As a S&OP 담당자, I want 기간계 데이터가 자동으로 모이기를 so that 매일 아침 내려받고 합치는 일을 하지 않는다.

**Why P1**: 고객의 필수 요구사항이다.

**Requirement**: COL-01

**Acceptance Criteria**:

1. WHEN 정해진 수집 시각이 되면 THEN 시스템 SHALL 접근이 승인된 원천을 조회해 원본을 `raw/<원천>/YYYYMMDD/`에 저장한다
2. WHEN 한 일자의 수집이 끝나면 THEN 시스템 SHALL 그 일자의 입력 구성을 시작한다
3. IF 원천 조회가 실패하면 THEN 시스템 SHALL 그 일자 입력 묶음의 상태를 `실패`로 기록하고 실패한 원천의 이름을 남긴다
4. WHEN S&OP 담당자가 재수집을 요청하면 THEN 시스템 SHALL 그 일자의 수집을 다시 실행하고 이전 수집분을 지우지 않는다
5. WHERE 원천의 갱신 주기가 매일이 아닌 경우(판매예측 주 1회) 시스템 SHALL 가장 최근 수집분을 그 일자의 입력 묶음에 넣는다

**Independent Test**: 정보계의 코드표 1종을 수집 대상으로 두고 파이프라인을 실행하면 `raw/`에 원본이, `input/`에 현행 형식 파일이 생긴다.

### P1: 입력 묶음 구성 ⭐ MVP

**User Story**: As a S&OP 담당자, I want 수집한 데이터가 현행과 같은 파일로 만들어지기를 so that 프로그램을 고치지 않고 실행한다.

**Why P1**: 프로그램이 파일 이름과 컬럼 순서에 의존한다.

**Requirement**: INPUT-01

**Acceptance Criteria**:

1. WHEN 입력 구성이 실행되면 THEN 시스템 SHALL `input/YYYYMMDD/`에 기간계 입력(재고, 판매예측, 코드표 5종)을 현행 파일 이름과 형식(재고 CSV utf-8-sig, 코드표 5종 CSV cp949)으로 만든다
2. The 시스템 SHALL 입력 묶음마다 파일별 출처, 수집 시각, 행 수, 내용 지문을 적은 명세서를 저장한다
3. WHEN S&OP 담당자가 재고 카테고리별 엑셀 6개를 올리면 THEN 시스템 SHALL 고객의 합본 스크립트(merge_excel_to_csv.py)로 합본 CSV 1개를 만든다
4. WHEN S&OP 담당자가 자동 수집되지 않는 원천의 파일을 올리면 THEN 시스템 SHALL 그 파일을 해당 일자의 입력 묶음에 넣고 명세서의 출처를 `올린 파일`로 적는다
5. IF 수집한 재고로 기준 72개 컬럼을 만들 수 없으면 THEN 시스템 SHALL 입력 묶음의 상태를 `실패`로 기록하고 빠진 컬럼의 이름을 남긴다

**Independent Test**: 기준 입력의 카테고리별 재고 엑셀을 올리면 고객 PC의 합본 CSV와 내용 지문이 같은 파일이 생긴다.

### P1: 입력 검증 ⭐ MVP

**User Story**: As a S&OP 담당자, I want 입력이 온전하지 않으면 실행되지 않기를 so that 빠진 데이터로 만든 결과를 ERP에 올리지 않는다.

**Why P1**: 실제로 부분 추출 사고가 있었다.

**Requirement**: VAL-01

**Acceptance Criteria**:

**Requirement**: OPS-01

**Acceptance Criteria**:

1. WHEN S&OP 담당자가 [지금 실행]을 누르면 THEN 시스템 SHALL 운영 버전, 운영 파라미터, 당일 입력 묶음으로 운영용 실행기에서 실행을 시작한다
2. IF 당일 입력 묶음의 상태가 `준비됨`이 아니면 THEN 시스템 SHALL 실행을 시작하지 않고 입력 묶음의 상태를 보여준다
3. WHEN 운영 실행이 정상 종료하면 THEN 시스템 SHALL 결과 파일을 `prod/YYYYMMDD/<실행ID>/`에 저장한다
4. WHEN 운영 실행이 `완료`되면 THEN 시스템 SHALL 직전 운영 실행 결과와의 건수 4종 차이를 보여준다
5. WHEN S&OP 담당자가 `완료`된 운영 실행에 [승인]을 누르면 THEN 시스템 SHALL 실행 상태를 `승인됨`으로 바꾸고 승인자와 일시를 기록한다
6. IF 실행 상태가 `규칙위반`이면 THEN 시스템 SHALL 승인 요청을 거절한다
7. WHILE 운영 실행이 `승인됨`이 아닌 동안 시스템 SHALL ERP 업로드 파일의 내려받기를 거절한다
8. WHEN S&OP 담당자가 `승인됨` 실행의 내려받기 화면을 열면 THEN 시스템 SHALL 파일을 ① 재고전환_온오프 ② 양수도 ③ 재고전환_오프온 순서로 보여준다
9. WHEN 같은 일자에 운영 실행을 다시 하면 THEN 시스템 SHALL 새 실행 ID로 저장하고 이전 실행의 결과를 지우지 않는다

**Independent Test**: 준비된 입력 묶음으로 [지금 실행] → 결과 확인 → [승인] → 내려받기 화면에 파일이 업로드 순서대로 나온다.

### P2: 운영 반영 요청과 승인

**User Story**: As a IT혁신팀, I want 회귀 테스트 결과를 보고 새 버전의 운영 반영을 승인하기를 so that 확인되지 않은 프로그램이 운영에 쓰이지 않는다.

**Why P2**: 검증 실행과 결과 비교가 있어야 성립한다.

**Requirement**: PROMO-01

**Acceptance Criteria**:

1. WHEN 현업 사용자가 검증 실행이 `완료`된 버전에 [운영 반영 요청]을 누르면 THEN 시스템 SHALL 기준 입력으로 그 버전과 현재 운영 버전을 함께 실행한다
2. IF 그 버전의 가장 최근 검증 실행이 `완료`가 아니면 THEN 시스템 SHALL 운영 반영 요청을 거절한다
3. WHEN 회귀 실행 두 건이 끝나면 THEN 시스템 SHALL IT혁신팀에게 두 결과의 비교와 규칙 5개의 결과를 보여준다
4. WHEN IT혁신팀이 [승인]을 누르면 THEN 시스템 SHALL 그 버전의 상태를 `운영`으로, 이전 운영 버전의 상태를 `보관`으로 바꾼다
5. WHEN IT혁신팀이 [반려]를 누르면 THEN 시스템 SHALL 그 버전의 상태를 `반려`로 바꾸고 의견을 기록한다
6. IF 새 버전의 회귀 실행이 `규칙위반`이나 `실행오류`로 끝났으면 THEN 시스템 SHALL 승인을 거절한다
7. WHEN IT혁신팀이 `보관` 상태의 버전에 [되돌리기]를 누르면 THEN 시스템 SHALL 그 버전을 `운영`으로, 현재 운영 버전을 `보관`으로 바꾼다

**Independent Test**: 새 버전을 요청 → 회귀 결과 화면 → [승인] 후 다음 운영 실행 기록에 새 버전이 적힌다.

### P2: 이상치 질문·답변과 재테스트

**User Story**: As a 현업 사용자, I want 검증 결과의 이상치를 작성자와 점별 바이어에게 묻고 답을 반영해 다시 돌려 보기를 so that 이상한 결과의 사유를 확인한 뒤 운영 반영을 요청한다.

**Why P2**: 검증 실행과 결과 비교가 있어야 성립한다. 이상치 기준과 문의 대상은 고객 확인이 필요하다 (Q23~Q25).

**Requirement**: QA-01

**Acceptance Criteria**:

1. WHEN 검증 실행이 `완료`되면 THEN 시스템 SHALL 이상치(이동 건수 이상, 과다 이동)를 뽑아 검증 결과에 종류, 상품, 내용, 문의 대상과 함께 보여준다
2. WHEN 현업 사용자가 [질문 목록 만들기]를 누르면 THEN 시스템 SHALL 이상치마다 문의 대상(프로그램 작성자 또는 해당 점 바이어)과 질문 문안을 가진 질문 목록을 만든다
3. WHEN 현업 사용자가 질문 목록 내려받기를 누르면 THEN 시스템 SHALL 질문번호, 받는 사람, 상품코드, 상품명, 이상 내용, 질문, 답변 선택, 답변 내용 열을 가진 CSV 파일을 내려준다
4. WHEN 현업 사용자가 [질문 보내기]를 누르면 THEN 시스템 SHALL 질문 목록의 상태를 `보냄`으로 바꾸고 보낸 시각을 기록한다
5. WHEN 받는 사람이 화면에서 답변 유형과 내용을 저장하면 THEN 시스템 SHALL 답변을 답변자, 일시와 함께 기록한다
6. WHEN 현업 사용자가 답변이 적힌 질문 목록 파일을 올리면 THEN 시스템 SHALL 질문번호가 같은 질문에 그 행의 답변을 기록한다
7. IF 올린 파일의 답변 선택이 그 질문에 허용된 유형(정상, 이동 제외, 파라미터 조정, 로직 수정 중 질문별 허용 유형)이 아니면 THEN 시스템 SHALL 그 행을 기록하지 않고 질문번호와 허용 유형을 보여준다
8. IF 바이어가 자기에게 온 질문이 아닌 질문에 답하려 하면 THEN 시스템 SHALL 그 답변을 거절한다
9. WHEN 답변이 1건 이상 기록되면 THEN 시스템 SHALL 반영 계획(파라미터 변경, 이동 제외 상품, 사유가 확인된 항목, 프로그램 수정이 필요한 항목, 답변이 없는 항목)을 보여준다
10. WHEN 현업 사용자가 [답변 반영해 재테스트]를 누르면 THEN 시스템 SHALL 원래 실행의 프로그램 버전과 입력 일자에 파라미터 조정 답변의 제안값과 이동 제외 답변의 상품을 반영해 검증 실행을 시작한다
11. The 시스템 SHALL 이동 제외 답변을 제외·전용 SKU 마스터의 임시 사본에만 추가하고 등록된 마스터 버전을 바꾸지 않는다
12. WHEN 재테스트가 `완료`되면 THEN 시스템 SHALL 이상치마다 처리 상태(해소, 확인됨, 남음)와 원래 실행 대비 건수 차이를 보여준다

**Independent Test**: 검증 실행 결과에서 질문 목록을 만들고 답변이 적힌 파일을 올려 재테스트하면, 이동 제외로 답한 상품의 이동이 빠지고 이상치 상태가 `해소`로 나온다. 등록된 마스터 버전 목록은 그대로다.

### P2: 실행 이력

**User Story**: As a IT혁신팀, I want 누가 언제 어떤 프로그램과 설정으로 실행했는지 보기를 so that 결과의 근거를 추적한다.

**Why P2**: 기록은 P1에서 쌓이고, 조회 화면이 여기서 추가된다.

**Requirement**: HIST-01

**Acceptance Criteria**:

1. WHEN 사용자가 실행 이력을 열면 THEN 시스템 SHALL 일시, 모드, 실행자, 프로그램 버전, 입력 일자, 마스터 버전, 요약 건수, 소요 시간, 상태를 최신순으로 보여준다
2. The 시스템 SHALL 입력 묶음, 결과 파일, 실행 기록을 지우는 기능을 제공하지 않는다

**Independent Test**: 검증 실행 2건과 운영 실행 1건 뒤에 이력을 열면 3건이 최신순으로 나온다.

### P3: 정해진 시각의 자동 시작

**User Story**: As a S&OP 담당자, I want 수집이 끝나면 운영 실행이 자동으로 시작되기를 so that 출근했을 때 결과가 준비되어 있다.

**Why P3**: 사람 확인 없이 자동 시작해도 되는지 고객 답이 필요하다 (Q9). PoC는 시연 수준이다.

**Requirement**: SCHED-01

**Acceptance Criteria**:

1. WHERE 자동 시작이 켜져 있을 때 WHEN 수집 파이프라인이 입력 준비됨을 알리면 THEN 시스템 SHALL 그 일자의 운영 실행을 시작한다
2. WHERE 자동 시작이 꺼져 있을 때 시스템 SHALL 입력 준비됨 알림을 받아도 운영 실행을 시작하지 않는다
3. IF 같은 일자의 입력 준비됨 알림이 다시 오면 THEN 시스템 SHALL 자동 실행을 다시 시작하지 않는다

### P3: 알림

**User Story**: As a S&OP 담당자, I want 실패와 완료를 알림으로 받기를 so that 화면을 계속 보고 있지 않아도 된다.

**Why P3**: 알림 채널이 미정이다 (Q16). PoC는 시연 수준이다.

**Requirement**: NOTI-01

**Acceptance Criteria**:

1. WHEN 수집이 실패하면 THEN 시스템 SHALL S&OP 담당자에게 실패한 원천의 이름을 담은 알림을 보낸다
2. WHEN 운영 실행이 `입력실패`가 되면 THEN 시스템 SHALL S&OP 담당자에게 실패한 검증 항목을 담은 알림을 보낸다
3. WHEN 운영 실행이 `완료`나 `규칙위반`으로 끝나면 THEN 시스템 SHALL S&OP 담당자에게 상태와 요약 건수를 담은 알림을 보낸다
4. WHEN 운영 반영 요청의 회귀 실행이 끝나면 THEN 시스템 SHALL IT혁신팀에게 승인 요청 알림을 보낸다

---

### P3: 현행 대비 시간 측정

**User Story**: As a IT혁신팀, I want 클라우드 방식이 현행보다 얼마나 걸리는지 보기를 so that PoC의 성과를 수치로 판단한다.

**Why P3**: 고객 PPT 2쪽의 "기존 방식과 차이점 확인(업무시간 등)"이다.

**Requirement**: MEAS-01

**Acceptance Criteria**:

1. The 시스템 SHALL 운영 실행마다 수집 시작, 입력 준비됨, 실행 시작, 실행 종료, 승인의 시각을 기록하고 구간별 소요 시간을 보여준다

## Edge Cases

- IF 입력 일자에 해당하는 입력 묶음이 없으면 THEN 시스템 SHALL 실행 요청을 거절하고 선택할 수 있는 일자 목록을 보여준다
- IF 운영 상태인 버전이 없으면 THEN 시스템 SHALL 운영 실행 요청을 거절하고 "운영 버전이 지정되지 않았습니다"를 보여준다
- IF 마스터 2종 중 올린 버전이 없는 종류가 있으면 THEN 시스템 SHALL 그 파일 없이 실행하고 입력 검증 결과에 경고로 기록한다
- WHEN 프로그램이 결과 파일을 하나도 만들지 않고 정상 종료하면 THEN 시스템 SHALL 실행 상태를 `실행오류`, 사유를 `결과 없음`으로 기록한다
- IF 실행기를 시작하지 못하면 THEN 시스템 SHALL 실행 상태를 `실행오류`, 사유를 `실행기 시작 실패`로 기록한다
