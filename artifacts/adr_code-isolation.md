# ADR: 검증용과 운영용 실행기를 나누고 권한으로 격리한다

## Status

Proposed

## Context

현업이 AI 도구로 고친 프로그램을 그대로 올려 실행한다. 개발자의 검토를 거치지 않은 코드가 실제 재고·판매 데이터를 읽는다.

악의보다는 실수가 걱정이다. 잘못 고친 프로그램이 운영 결과를 덮어쓰거나, 입력을 바꾸거나, 데이터를 밖으로 보내거나, 끝없이 도는 경우다. 요구사항 문서의 실패 조건 중 하나가 "검증용 결과가 운영 결과와 섞여 ERP에 올라갈 수 있다"이다.

## Decision

같은 이미지로 실행기를 두 개 둔다.

| | 검증용 실행기 | 운영용 실행기 |
| --- | --- | --- |
| 실행하는 프로그램 | 등록된 모든 버전 | 승인된 운영 버전만 (관리 API가 확인) |
| 읽을 수 있는 곳 | 입력, 프로그램 | 입력, 프로그램 |
| 쓸 수 있는 곳 | 검증 결과 구역만 | 운영 결과 구역만 |

여기에 다음을 더한다.

- 실행기는 외부로 통신할 수 없다. 저장소만 접근한다
- 실행기는 기록 DB에 접근하지 않는다
- 현업의 프로그램은 컨테이너 안에서 권한이 제한된 별도 사용자로 실행하고, 저장소 접근 권한을 넘겨주지 않는다. 프로그램은 작업 폴더의 파일만 읽고 쓴다
- 실행 시간과 CPU·메모리에 상한을 둔다
- 등록할 때 문법과 허용되지 않은 라이브러리 사용을 검사한다. 이 검사는 실수를 일찍 알려 주는 용도이고, 격리의 수단은 위의 권한과 통신 차단이다
- 검증 실행 결과 파일에는 파일 이름과 시트 첫 줄에 검증용임을 표시한다

## Rationale

- "검증용이 운영 결과를 못 쓴다"를 코드의 약속이 아니라 Azure 권한으로 보장한다. 프로그램이 무엇을 하든 권한 밖의 일은 일어나지 않는다
- 입력은 양쪽 모두 읽기만 하므로 수집한 데이터가 바뀌지 않는다
- 외부 통신을 막으면 데이터 반출 경로가 없어진다

## Alternatives Considered

### Alternative 1: 실행기 하나, 권한 하나
- **Pros**: 구성이 단순하다
- **Cons**: 검증 실행이 운영 결과 구역에 쓸 수 있다. 막는 것은 실행 틀의 코드뿐이다
- **Why Not**: 실패 조건을 코드의 정확성에만 맡기게 된다

### Alternative 2: 등록할 때의 정적 검사만으로 막는다
- **Pros**: 실행 구조를 바꾸지 않는다
- **Cons**: 검사는 우회될 수 있고, AI가 만든 코드는 형태가 다양하다
- **Why Not**: 검사는 보조 수단으로만 쓴다

### Alternative 3: 개발자가 검토한 뒤에만 실행한다
- **Pros**: 가장 안전하다
- **Cons**: 현업이 직접 고쳐 바로 돌려 보는 방식이 끊긴다
- **Why Not**: PoC의 목적(현업이 고친 프로그램을 올려 실행·검증)과 맞지 않는다. 대신 운영 반영에만 승인을 둔다

## Consequences

### Positive
- 검증 실행이 운영에 영향을 주지 못한다는 것을 권한 설정으로 보여 줄 수 있다
- 고객 PPT 5쪽의 "보안 검증", "접근 통제"에 대응하는 구체적 수단이 된다

### Negative
- 실행기와 권한 설정이 두 벌이다
- 외부 통신이 막혀 있어 프로그램이 인터넷의 자료를 쓰는 수정은 할 수 없다

### Risks
- 컨테이너 안에서 프로그램에 저장소 권한이 넘어가지 않게 하는 구체적 방법은 PoC 초기에 시험으로 확인한다: 쓰기와 외부 접속을 시도하는 시험용 프로그램을 돌려 본다
- 현업 사용자와 S&OP 담당자가 같은 사람이면(Q4) 역할 분리의 의미가 줄어든다: 그래도 실행기 권한 분리는 유지한다
