# ADR: 데이터 수집은 Data Factory로 원본을 가져오고, 입력 구성을 따로 둔다

## Status

Proposed

## Context

기간계 8종(재고, 판매예측, 공헌이익, 코드표 5종)을 자동으로 모아야 한다. 고객의 필수 요구사항이고, 수집 수단은 Azure Data Factory로 정해졌다(요구사항 문서 D1).

걸리는 조건이 셋이다.

- 현행 프로그램은 고치지 않는다. 입력은 현행과 같은 파일 이름과 형식이어야 한다
- 현행 형식이 파일마다 다르다. 재고는 CSV(utf-8-sig) 72개 컬럼, 판매예측은 엑셀, 공헌이익은 UTF-16 탭 구분, 코드표는 CSV(cp949)다
- 프로그램이 재고 컬럼을 순서로 읽는다. 순서가 하나만 어긋나도 조용히 틀린 값이 들어간다

## Decision

수집을 두 단계로 나눈다.

1. **수집 (Data Factory)**: 원천을 조회해 원본 그대로 저장소의 `raw/` 구역에 둔다. 고객 내부망에 수집 중계 서버(Self-hosted Integration Runtime)를 두고 전용선·VPN으로 연결한다
2. **입력 구성 (Container Apps Job)**: 원본을 현행 파일 이름과 형식으로 바꿔 `input/YYYYMMDD/`에 둔다

접근이 승인되지 않은 원천은 사람이 화면 내려받기 파일을 올리고, 같은 입력 구성 단계가 받아 처리한다.

## Rationale

- Data Factory는 엑셀 파일을 읽을 수는 있지만 쓸 수 없다. 판매예측의 현행 형식(엑셀)을 ADF만으로는 만들 수 없다
- 형식 변환을 한 곳에 모으면, 자동 수집이든 파일 올리기든 그 뒤는 같다. 한 원천이 막혀도 나머지가 멈추지 않는다
- 원본을 남겨 두면 변환이 잘못됐을 때 다시 수집하지 않고 변환만 다시 할 수 있다. 재고는 과거 시점을 다시 조회할 수 없으므로 이 점이 중요하다
- 변환 규칙(컬럼 순서, 인코딩)이 프로그램과 같은 Python으로 관리되어 기준 입력 표본과 대조하기 쉽다

## Alternatives Considered

### Alternative 1: Data Factory에서 최종 파일까지 직접 만든다
- **Pros**: 구성요소가 하나 줄어든다
- **Cons**: 엑셀을 쓸 수 없다. 인코딩과 2행 헤더 같은 현행 형식을 ADF 설정으로 맞추기 어렵다
- **Why Not**: 프로그램을 고치지 않는다는 원칙을 지킬 수 없다

### Alternative 2: 수집 프로그램을 직접 만든다 (Python으로 DB 조회)
- **Pros**: 수집과 변환이 한 프로그램에 있다
- **Cons**: 일정 관리, 재시도, 접속 정보 관리, 감시를 직접 만들어야 한다
- **Why Not**: 사용자가 ADF를 기본안으로 정했다. 본사업에서 원천이 늘어날 때도 ADF가 유리하다

### Alternative 3: 전부 사람이 올린다 (PPT 2쪽의 2안)
- **Pros**: 기간계 접근 승인이 필요 없다. 가장 빨리 시작할 수 있다
- **Cons**: 고객의 필수 요구사항을 입증하지 못한다
- **Why Not**: 기본안이 아니다. 다만 막힌 원천의 대체 경로로 남긴다

## Consequences

### Positive
- 자동 수집과 파일 올리기가 같은 저장 구조로 모인다
- 수집 시각과 출처가 입력 묶음마다 기록된다

### Negative
- 구성요소가 하나 늘어난다 (입력 구성)
- 고객 내부망에 수집 중계 서버를 설치하고 운영해야 한다

### Risks
- L-lit 재고의 원천 테이블을 모른다: 착수 즉시 확인한다(Q1). 원천 조회 결과와 화면 내려받기 파일을 같은 시각에 대조하는 시험을 먼저 한다
- 대량 조회가 기간계에 부하를 준다: 조회 시간대와 조건을 고객 DB 담당자와 정한다(Q1)
- 수집 중계 서버가 1대다: PoC에서는 파일 올리기로 우회한다
