# ADR: 실행기는 Container Apps Job으로 하고, 고정 이미지에 프로그램 파일을 넣어 실행한다

## Status

Proposed

## Context

현행 pipeline.py를 고치지 않고 클라우드에서 실행해야 한다. 조건은 다음과 같다.

- 프로그램이 전역 변수에 상태를 두어 한 프로세스에서 두 건을 동시에 돌릴 수 없다 (PDF 5-⑥)
- 실행은 몇 분 걸리는 일괄 처리다. 부분 추출 입력으로 약 200초이고, 전체 추출 입력의 시간은 아직 모른다
- 현업이 프로그램을 자주 고쳐 올린다. 올릴 때마다 오래 기다리면 다시 개인 PC로 돌아간다
- 결과 재현을 위해 Python과 라이브러리 버전을 현행 PC와 같게 고정한다

## Decision

Azure Container Apps Job을 실행기로 쓴다. 실행 1건마다 컨테이너 하나가 떠서 일을 마치고 사라진다.

이미지는 하나로 고정한다(Python 3.14.7과 현행 라이브러리 버전, 실행 틀). 현업의 pipeline.py는 이미지에 넣지 않고, 실행이 시작될 때 저장소에서 가져온다.

## Rationale

- 실행마다 새 컨테이너라 전역 변수 문제가 프로그램 수정 없이 사라진다
- 프로그램을 올리면 이미지를 다시 만들지 않고 바로 실행할 수 있다
- 일정으로도, 요청으로도 시작할 수 있어 검증 실행과 운영 실행을 같은 방식으로 다룬다
- 돌지 않을 때는 비용이 들지 않는다. 하루 몇 건 수준의 PoC에 맞다

## Alternatives Considered

### Alternative 1: Azure Functions
- **Pros**: 가장 단순하다. 일정 트리거가 기본으로 있다
- **Cons**: 실행 시간 제한이 있고, 같은 프로세스가 여러 요청을 받을 수 있어 전역 변수 문제가 남는다
- **Why Not**: 전체 추출 입력의 실행 시간을 모르는 상태에서 시간 제한을 안고 갈 수 없다

### Alternative 2: 프로그램 버전마다 이미지를 새로 만든다
- **Pros**: 버전별로 라이브러리를 다르게 할 수 있다. 이미지 자체가 버전 기록이 된다
- **Cons**: 올릴 때마다 빌드를 기다려야 한다. 빌드 과정이 하나 더 생긴다
- **Why Not**: PoC에서 등록 단위는 pipeline.py 파일 하나이고 새 라이브러리는 받지 않는다(D9). 본사업에서 라이브러리 변경이 필요해지면 이 방식으로 넓힌다

### Alternative 3: Azure Batch, AKS
- **Pros**: 대량·병렬 처리에 강하다
- **Cons**: 구성과 운영 부담이 크다
- **Why Not**: 하루 몇 건, 수 분짜리 실행에는 과하다

## Consequences

### Positive
- 현행 프로그램을 그대로 쓴다
- 실행기가 프로그램 내부를 모르므로, 본사업에서 다른 프로그램을 같은 틀에 올릴 수 있다

### Negative
- 새 라이브러리가 필요한 수정은 이미지 변경(개발팀 작업)이 필요하다
- 실행마다 컨테이너가 뜨는 시간과 입력을 가져오는 시간이 더해진다

### Risks
- 한국어 Windows에서 만든 프로그램이 Linux 컨테이너에서 다르게 동작할 수 있다: Linux에서 수정 없이 실행됨은 확인했다(`docs/reproduction-report.md`). 같은 입력의 PC 결과를 받아 대조하고, 다르면 Windows 실행 환경으로 바꾸며, 그때 이 결정을 다시 한다
- 실행 시간과 메모리: 2026-11-18 입력(재고 12.7만 행)으로 65~68초, 약 1GB가 측정됐다. Python 3.14.7에서는 아직 시험하지 못했다
