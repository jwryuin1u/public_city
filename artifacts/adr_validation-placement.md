# ADR: 입력 검증과 결과 검증은 실행 컨테이너 안에서 프로그램 앞뒤로 한다

## Status

Proposed

## Context

실행마다 두 가지 검증이 필요하다. 실행 전에 입력이 온전한지(파일, 컬럼, 6개 카테고리, 10개 점, 갱신 주기), 실행 후에 결과가 업무 규칙 5개를 지키는지다. 검증 실행과 운영 실행 모두에 같은 검증이 적용되어야 한다.

초안 v0.1은 "Azure Functions 또는 실행 컨테이너 내 전·후처리"로 열어 두었다.

## Decision

두 검증을 실행 컨테이너 안의 실행 틀이 수행한다. 순서는 입력 검증 → 프로그램 실행 → 결과 검증이다. 입력 검증이 실패하면 프로그램을 실행하지 않는다.

검증 코드는 우리가 만든 실행 틀에 있고 이미지에 들어 있다. 현업이 올리는 pipeline.py와 분리되어 있어 현업의 수정이 검증을 바꿀 수 없다.

두 실행 결과의 비교(건수 차이, 달라진 SKU)는 관리 API가 한다. 비교는 두 실행이 모두 끝난 뒤에야 할 수 있기 때문이다.

## Rationale

- 두 모드가 같은 이미지의 같은 검증을 쓴다. 검증 실행에서 통과한 것이 운영 실행에서 다르게 판정될 일이 없다
- 입력, 결과, 검증 결과가 한 실행의 결과 폴더에 함께 남는다. 어느 입력으로 어떤 판정이 났는지 추적하기 쉽다
- 검증에 필요한 것(입력 파일, 파라미터, 결과 파일)이 이미 컨테이너 안에 있다. 다른 서비스로 옮겨 다시 읽지 않는다
- 서비스가 하나 줄어든다

## Alternatives Considered

### Alternative 1: 별도 Azure Functions
- **Pros**: 검증만 따로 배포하고 따로 실행할 수 있다
- **Cons**: 수십 MB의 입력과 결과를 다시 읽어야 한다. 실행과 검증 사이의 순서와 실패 처리를 따로 엮어야 한다
- **Why Not**: PoC 규모에서 얻는 것보다 엮는 비용이 크다

### Alternative 2: 관리 API 안에서 검증한다
- **Pros**: 검증 결과를 DB에 바로 쓴다
- **Cons**: 화면 응답을 맡는 웹 앱이 큰 파일 처리를 함께 한다
- **Why Not**: 화면이 느려지고 웹 앱의 자원 산정이 어려워진다

## Consequences

### Positive
- 실행 1건이 "입력 확인부터 결과 판정까지" 한 단위가 된다
- 입력 검증만 먼저 돌려 보는 것도 같은 실행기로 할 수 있다 (프로그램 실행 단계를 건너뛰는 지시)

### Negative
- 검증 규칙을 고치면 실행 이미지를 다시 배포해야 한다
- 실행 틀이 재고배분의 입력·결과 형식을 안다. 다른 프로그램을 올리려면 프로그램별 검증 묶음을 따로 꽂는 구조가 필요하다 (본사업 과제)

### Risks
- 현행 결과가 규칙 5개를 통과하지 못할 수 있다: 0812로 먼저 확인하고, 통과하지 못하는 규칙의 차단 여부를 고객과 다시 정한다
- 규칙의 정확한 계산식은 소스의 CLAUDE.md를 받아야 확정된다
