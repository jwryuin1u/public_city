# 변경 요약: 기존 자료에서 가져온 것, 바꾼 것, 그 이유

2026-11-17 · 대상: TO-BE 설계 초안 v0.1(md)과 고객 자료(기초정보 PDF, IT혁신팀 PPT)

고객 자료 두 건은 1차 근거로 그대로 썼다. 초안 v0.1은 참고 자료로 보고 항목별로 채택 여부를 정했다.

## 그대로 가져온 것

| 초안 항목 | 지금 있는 곳 |
| --- | --- |
| 실행기 하나에 검증 실행과 운영 실행 두 모드 | 요구사항 확정서 6장, 설계서 전체 |
| 현행 pipeline.py를 고치지 않고 컨테이너로 실행, 실행 1건당 컨테이너 1개 | `adr_execution-runner.md` |
| 실행 1건 = 프로그램 버전 + 파라미터 + 입력 일자, 실행 기록에 남김 | 명세 RUN-01, PARAM-01 |
| 파라미터 초기값은 코드 기본값이 아닌 현재 운영값 | 명세 PARAM-01 |
| 업무 규칙 5개 자동 확인, 위반 시 승인과 운영 반영 요청 차단 | 명세 RULE-01, OPS-01, PROMO-01 |
| 검증 결과와 운영 결과 분리, 검증 결과에 TEST_ 표시 | 명세 RUN-01, ISO-01 |
| 화면 8개(S1~S8)와 사용자 행동 | 설계서 구성요소 ④ |

| ERP 자동 연계, 로직 변경, 다른 프로그램 수용, LLM 연계는 범위 밖 | 명세 Out of Scope |

## 바꾼 것

| 초안 | 바꾼 내용 | 이유 |
| --- | --- | --- |
| 재고 컬럼이 프로그램이 기대하는 이름·위치와 다르면 중단 | 등록된 기준 72개 컬럼과 이름·순서가 같은지만 확인. 컬럼 위치 오류는 PoC에서 고치지 않음 | 현행 프로그램은 이미 69번 자리에서 발주번호를 읽는다. 초안대로면 항상 중단되고, 고치면 현행 결과와 비교할 수 없다 |
| 0812·0813 둘 다 회귀 기준, 동시에 0813은 차단 대상 | 회귀 기준은 0812만. 0813은 차단 사례로만 사용 | 0813은 4개 카테고리만 있는 부분 추출이다. 재현 기준과 차단 대상이 동시에 될 수 없다 |
| 수집할 때 인코딩을 UTF-8로 통일 | 현행 파일 이름·형식·인코딩 그대로 | 공헌이익은 UTF-16 탭 구분이다. 바꾸면 프로그램이 다르게 읽을 수 있고, "프로그램을 고치지 않는다"와 충돌한다 |
| Data Factory가 수집과 병합까지 | Data Factory는 원본만 가져오고, 입력 구성 단계가 현행 형식으로 변환 | ADF는 엑셀을 쓸 수 없고 현행 형식이 파일마다 다르다. 파일 올리기 경로도 같은 단계로 받는다 |
| 접근이 어려우면 화면 올리기로 대체하고 재고 1종만 시범 연계 | ADF 자동 수집이 기본. 접근이 승인되지 않은 원천만 파일로 올림 | 사용자 결정. 또 재고는 원천 테이블이 확인되지 않아 시범 대상으로 고정할 수 없다 |
| 실행기 하나 + "시스템이 코드 검사" | 검증용·운영용 실행기를 나누고 Azure 권한과 외부 통신 차단으로 격리 | 검토 없이 올린 프로그램의 결과가 운영 결과에 섞이는 것을 검사가 아니라 권한으로 막는다 |
| 검증 위치: Azure Functions 또는 컨테이너 내 처리 | 실행 컨테이너 안에서 프로그램 앞뒤로 | 두 모드가 같은 검증을 쓰고 서비스가 줄어든다 |
| 실행 기록 항목 | 마스터 버전 추가 | 마스터가 바뀌면 같은 입력도 결과가 달라진다 |
| 운영 반영 요청·승인은 시연 수준 | 운영 결과 승인, 운영 반영 요청·승인을 구현 범위로 | "규칙 위반 시 승인이 막힌다"는 인수 기준을 확인하려면 실제로 동작해야 한다 |
| 비교 대상: 같은 일자의 운영 결과, 0812/0813 기준 결과 | 항상 같은 날 클라우드에서 실행한 결과끼리 비교 | 프로그램이 실행일 날짜를 써서, 다른 날 만든 결과와 비교하면 날짜 차이가 섞인다 |
| 실행 환경 Python 3.10 이상 | Python 3.14.7, pandas 3.0.5, numpy 2.5.3, openpyxl 3.1.5 고정 | 결과 재현이 인수 기준이다 |
| 실행 약 200초 | 부분 추출 입력 기준임을 명시, 전체 추출은 측정 후 정함. 실행 상한 30분(가정) | 200초는 4.4만 행 입력의 측정치다. 전체 추출은 15.2만 행이다 |
| 날짜 판정을 입력 일자로 주입 | 날짜 고정 기능은 만들지 않음 | 프로그램 수정 없이 되는지 소스를 봐야 안다 |
| 운영 파라미터 9개 나열 | 14개 전체 (경고 민감도, 과다 이동 기준, 미등록 브랜드 정책, 점센터 보호, 헤더 행 추가). 숨은 값(반입경과 22개월)은 화면에 노출 | 고객 PDF 4-2, 4-3의 현재값 전체가 필요하다 |

## 새로 넣은 것

| 내용 | 이유 |
| --- | --- |
| PoC 기간에는 현행 PC가 실제 업무를 맡고 클라우드는 비교용으로 병행 | 고객은 PoC 성과를 본 뒤 본 구축에 착수한다 |
| 프로그램 등록 단위는 pipeline.py 파일 하나, 새 라이브러리는 받지 않음 | 등록 범위가 초안에 없었다 |
| 현행 대비 시간 측정 (명세 MEAS-01) | 고객 PPT 2쪽의 "기존 방식과 차이점 확인(업무시간 등)"이 초안에 빠져 있었다 |
| 고객 확인 사항 Q10~Q16 | 15시 이후 신청 건 처리 방식, 컬럼 오류 수정 시점, 숨은 파라미터 노출, 후속 분석, 원천 확정 시각, 병행 비교 기간, 로그인·알림 채널 |
| Key Vault, Container Registry, Log Analytics | 접속 정보, 실행 이미지, 로그를 둘 곳이 초안에 없었다 |
| 고객 PPT 5쪽 구상과의 대응표 | VDI, 개발/배포 환경, API Gateway가 이 설계의 어디에 해당하는지 초안에 없었다 |
| 한국어 Windows와 Linux 컨테이너의 차이를 첫 확인 항목으로 | 결과가 다르면 실행기 선택이 바뀐다 |

| 코드 버전의 Git 저장소 보관 | PoC는 저장소의 버전별 보관으로 충분하다. Git 보관은 본사업에서 정한다 |

## 확인하지 못한 것

- 초안이 인용한 요청 메일과 화면 예시 페이지를 받지 못했다. 화면은 표 수준으로만 다뤘다
- 현행 소스와 실데이터가 없다. 소스를 봐야 확정되는 가정 6개는 작업 T3에서 가장 먼저 확인한다
- Azure 서비스의 세부 동작(ADF의 엑셀 쓰기 불가, Container Apps Job의 권한 분리 방식 등)은 공식 문서로 대조하지 않았다
- 작업 문서의 테스트 이름과 명령은 계획이다. 실행해 본 것이 아니다
