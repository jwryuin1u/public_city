## 2. 무엇을, 왜 만드는가

### 지금의 방식

S&OP 담당자 한 명이 매일 09:00~10:30에 개인 PC에서 다음을 한다.

1. L-lit에서 재고를 카테고리별로 6번 내려받아 스크립트로 합친다
2. 정보계·L-DEX에서 내려받은 파일과 MD가 취합한 엑셀을 폴더에 넣는다 (입력 10종)
3. Streamlit 화면에서 파라미터를 확인하고 [재고배분 실행]을 누른다
4. 결과 엑셀을 ERP에 ①온→오프 ②양수도 ③오프→온 순서로 직접 올린다

배분 프로그램(pipeline.py, 1,764줄)은 현업이 AI 도구로 직접 만들고 고쳐 온 것이다.

### 이 방식의 문제

- 입력 수집이 손작업이라 빠뜨릴 수 있다. 실제로 6개 카테고리 중 4개만 추출된 날이 있었다 (2026-08-13)
- 프로그램이 재고 파일의 컬럼을 이름이 아닌 순서로 읽는다. ERP 화면에 컬럼이 하나 추가되면서 '코너' 자리에서 '발주번호'를 읽고 있다
- 설정과 결과가 담당자 PC에만 있어 공유되지 않고 이력이 남지 않는다
- 프로그램을 고친 뒤 결과가 맞는지 사람이 눈으로 확인한다. 자동 테스트가 없다
- 운영 중인 소스와 저장소의 소스가 다르다 (1,764줄과 1,561줄)

### PoC가 답해야 할 질문

현업이 고친 재고배분 프로그램을 Azure에 올려, 자동으로 모은 데이터로 실행하고, 결과가 맞는지 자동으로 확인할 수 있는가. 그리고 그 구조가 매일 자동 운영으로 이어질 수 있는가.

고객은 PoC의 성과를 확인한 뒤 전체 인프라 구축에 착수한다(PPT 2쪽). 따라서 PoC의 성공은 "기능이 많다"가 아니라 "현행과 같은 결과가 나오고, 차이가 나면 그 이유를 설명할 수 있다"이다.

### 하지 않는 것

- ERP 자동 반영. PoC에서는 결과 파일을 내려받아 지금처럼 직접 올린다 (고객도 협의 대상으로 분류)
- 배분 로직 자체의 변경과 코드 정리. 컬럼 위치 오류도 PoC에서는 고치지 않는다 (5장 D2)
- 재고배분 외 다른 프로그램의 수용. PPT 5쪽의 AI 샌드박스 구상은 본사업 방향이며, PoC는 재고배분 1종으로 구조를 검증한다
- LLM 서비스 연계. 의미가 정해지지 않았다 (8장 Q5)
- MD 마스터의 화면 편집. PoC는 엑셀 업로드와 버전 보관까지
- 점·채널 정의 등 코드에 고정된 규칙을 설정으로 빼는 일

### 이렇게 되면 실패다

기능이 동작해도 다음 중 하나에 해당하면 PoC는 실패로 본다.

- 같은 입력과 같은 파라미터로 실행했는데 현행 PC와 결과가 다르고, 그 이유를 설명하지 못한다
- 일부 카테고리가 빠진 재고로 실행이 끝까지 진행되어 결과 파일이 나온다
- 검증용으로 실행한 결과가 운영 결과와 섞여 ERP에 올라갈 수 있다
- 현업이 프로그램을 고쳐 반영하는 일이 지금보다 눈에 띄게 번거로워져 다시 개인 PC로 돌아간다

### 업무 규칙 5개 (R11)

고객 PDF 5-⑪의 검증 불변식이다. 별도의 한도 값이 있는 것이 아니라 결과가 지켜야 하는 관계식이다.

| 규칙 | 내용 |
| --- | --- |
| 총량 보존 | SKU별로 배분 전 총량과 배분 후 총량이 같다 |
| 최소보장 | 양도한 점의 양도 후 보유일수가 최소보장일수 이상이다 |
| 그룹 내 이동 | 점간 이동은 같은 양수도 그룹 안에서만 일어난다 |
| 발송 한도 | 한 점이 내보낸 수량의 합이 그 점의 보유 수량 이하다 |
| 전환 한도 | 온·오프 전환 신청수량이 해당 배치의 가용수량 이하다 |

정확한 판정식(어느 컬럼으로 계산하는지, 반올림)은 소스의 CLAUDE.md를 받은 뒤 확정한다.

### D1에 따르는 조건

ADF로 수집하려면 원천이 DB 조회나 파일로 접근 가능해야 한다. 고객 자료로 확인되는 원천별 상태는 다음과 같다.

| 입력 | 원천 | 자료에서 확인된 것 | 위험 |
| --- | --- | --- | --- |
| 판매예측 | 정보계 테이블 GB_20170089.MM_PRED_SL_QTY | 테이블명 확인 | 낮음 |
| 코드표 5종 | 정보계 LDFDWP 코드 테이블 | 원천 컬럼명 확인 | 낮음 |
| 재고 | L-lit 상태별 재고조회(SKU) 화면 | 화면에서 내려받는 방식만 확인. 원천 테이블과 조회문은 없음 | 높음 |
| 공헌이익 | L-DEX 다차원손익관리_NEW 리포트 | 리포트에서 내려받는 방식만 확인 | 높음 |

재고는 매일 바뀌고 수작업이 가장 많아 자동 수집의 가치가 가장 크지만, 화면 뒤의 테이블이 확인되지 않았다. 게다가 프로그램이 컬럼을 순서로 읽으므로, 수집 결과를 화면 내려받기 파일과 똑같은 72개 컬럼 순서와 합본 형식으로 만들어야 한다.

**작성자 제안:** 접근 승인이 PoC 기간 안에 나지 않는 원천은 같은 저장 위치에 파일을 올리는 방식으로 대신한다. 수집 방법만 다르고 그 뒤의 검증·실행·결과는 같으므로, 한 원천이 막혀도 PoC 전체가 멈추지 않는다.

## 6. 검토한 구조 세 가지

| 안 | 내용 | 장점 | 단점 |
| --- | --- | --- | --- |
| A. 실행기 하나, 두 모드 **(채택)** | 같은 실행기에 어떤 프로그램 버전과 파라미터를 넣느냐로 검증 실행과 운영 실행을 나눈다 | PPT의 "고친 프로그램을 돌려 보는 환경"과 PDF의 "매일 자동 수행"을 한 구조로 충족. 검증에서 확인한 것이 운영에서 그대로 재현된다 | 승인 절차와 화면이 늘어난다 |
| B. 운영 실행만 | 승인된 프로그램을 매일 자동 실행하고 파라미터만 화면에서 바꾼다. 프로그램 교체는 개발팀이 배포한다 | 가장 단순하고 빠르다 | 현업이 프로그램을 직접 고쳐 온 방식을 끊는다. PPT 2쪽의 "로직 수정 관리", "로직 수정 반영 확인"을 충족하지 못한다 |
| C. 범용 AI 샌드박스 | PPT 5쪽 구상 전체. 여러 프로그램을 등록·실행하는 플랫폼 | 본사업 방향과 일치 | PoC 범위를 크게 넘는다. 프로그램마다 입출력 규칙이 달라 재고배분 1종으로 검증하려는 목적이 흐려진다 |

A를 채택한다. 초안 v0.1의 구조와 같다. C로 확장할 수 있도록 실행기가 재고배분 프로그램의 내부를 알지 않게 한다. 실행기가 아는 것은 "입력 폴더, 파라미터 파일, 출력 폴더"뿐이다.

| | 검증 실행 | 운영 실행 |
| --- | --- | --- |
| 시작 | 현업 사용자가 요청 | 매일 정해진 시각, 또는 S&OP 담당자가 요청 |

| 데이터 | 고른 일자의 수집분 | 당일 수집분 |
| 결과의 쓰임 | 비교·확인. 내려받은 파일에 검증용 표시 | 승인 후 ERP 업로드 파일로 제공 |

### 사용자가 하는 일

1. (검증) 고친 프로그램을 올리고 이름과 메모를 붙인다
2. (검증) 버전, 데이터 일자, 비교 대상, 파라미터를 골라 실행한다
3. (검증) 건수 변화, 규칙 통과 여부, 달라진 SKU를 확인하고 운영 반영을 요청한다
4. (검증) IT혁신팀이 회귀 테스트 결과를 보고 승인하거나 반려한다
5. (운영) MD가 마스터 엑셀을 올린다 — 바뀌었을 때만
6. (운영) 입력 검증에 경고나 실패가 있을 때만 담당자가 계속 또는 재수집을 고른다
7. (운영) 담당자가 결과를 확인하고 승인한다
8. (운영) ERP 업로드 파일을 내려받는다

## 7. PoC 범위와 인수 기준

| 구분 | 항목 |
| --- | --- |
| 구현 | ADF 수집 파이프라인(접근 가능한 원천), 입력 검증, 프로그램 등록·버전 보관, 검증 실행, 결과 검증(규칙 5개·비교), 이상치 질문 목록 생성·답변 수집·재테스트, 결과 조회·내려받기, 마스터 업로드, 파라미터·실행 이력 저장, 담당자 요청에 의한 운영 실행, 운영 결과 승인과 운영 반영 요청·승인(규칙 위반 시 차단 포함) |
| 시연 수준 | 정해진 시각의 자동 시작, 알림, 실행 이력 조회 화면 |
| 방식 확인만 | 사용자·권한 관리 화면, 스케줄 관리 화면 |
| 범위 밖 | 3장 "하지 않는 것" |

### 인수 기준 (안)

1. 기준 입력과 운영 파라미터로 실행한 결과가 현행 PC의 결과와 같다
2. 사용자가 고친 프로그램을 올려 실행하고, 운영 버전 결과와의 차이를 화면에서 확인할 수 있다
3. 파라미터를 바꿔 실행한 결과가 현행 PC에서 같은 파라미터로 실행한 결과와 같다
4. 대상 카테고리가 빠진 입력은 입력 검증에서 걸러져 실행되지 않는다
5. 업무 규칙 5개가 자동으로 확인되고, 위반이 있으면 표시되며 승인이 막힌다
6. 접근이 승인된 원천은 사람 손을 거치지 않고 수집되어 입력 묶음으로 저장된다
7. 수집부터 결과 확인까지 걸린 시간을 현행(09:00~10:30)과 비교해 제시한다
8. 검증 결과의 이상치로 질문 목록을 만들고, 답변을 반영한 재테스트 결과에서 이상치별 처리 상태를 확인할 수 있다

1번과 3번의 조건: 프로그램이 날짜 판정에 실행하는 날의 날짜를 쓰기 때문에, 8월에 만든 결과를 지금 다시 만들 수 없다. 고객 PC와 클라우드에서 같은 날 같은 입력으로 실행해 비교하거나, 실행 날짜를 고정하는 방법을 쓴다 (Q8). PC 쪽 실행은 고객 담당자의 협조가 필요하다.

7번은 D8의 병행 기간에 측정한다. 병행 일수와 측정 담당은 고객과 정한다 (Q15).

## 12. 이상치 질문·답변 추가 (2026-11-24)

고객과의 논의에서 나온 흐름을 PoC 구현 범위에 넣었다 (D12). 고객에게 보내는 To-Be 개발 방안의 협의 사항 19~21번이 Q23~Q25에 해당한다.

### 흐름

1. 검증 실행이 끝나면 이상치를 뽑아 검증 결과에 보여준다
2. 현업 사용자가 질문 목록을 만든다. 이상치마다 문의 대상과 질문 문안이 정해진다
3. 질문 목록을 파일(CSV)로 내려받거나 화면에서 보낸다
4. 받는 사람이 화면에서 답하거나, 답을 적은 파일을 현업 사용자가 다시 올린다
5. 답변 유형에 따라 반영 계획이 만들어지고, 현업 사용자가 재테스트를 실행한다
6. 재테스트 결과에 이상치별 처리 상태와 첫 실행 대비 차이가 나온다

### 기준 (기본안, 고객 확인 전)

| 항목 | 기본안 | 확인 |
| --- | --- | --- |
| 이상치 | 검토리포트의 경고 2종(이동 건수 이상, 과다 이동). 미충전 부족분은 하루 약 5천 건(2026-11-18 기준 5,051건)이라 기본 범위에서 뺐다 (사용자 결정 2026-11-24). 프로그램 버전 사이의 결과 차이는 이상치로 보지 않는다 (수정본 검증의 결과 비교에서 다룬다. 사용자 결정 2026-11-24) | Q23 |
